# SPMC-конвейерный ринг

**Статус:** архитектурное решение принято  
**Дата:** 2026-08-16

## Решение

Тракт команд от Ingress до Matcher реализуется как один ограниченный
**SPMC-конвейерный ринг с последовательными границами готовности**.

Один ринг и связанный с ним файл Command WAL обслуживают ровно один инструмент
внутри ровно одной эпохи. `(InstrumentId, EpochId)` фиксируется конфигурацией
тракта и manifest и не повторяется в каждом `CommandWalPayload`. Новая эпоха
создаёт новый файл Command WAL. `CommandSequence` монотонна в пределах файла.

`CommandSequence` равна `RecordHeader::sequence` физической записи Command WAL.
Отдельного счётчика или таблицы соответствия нет. Ingress получает sequence из
следующей абсолютной позиции ринга до публикации команды, а Persistence пишет
то же значение в заголовок физической записи.

Одна принятая входящая команда соответствует ровно одной физической записи
Command WAL. Это одинаково для торговых, управляющих и финансовых команд:
запись не содержит batch команд, а команда не разбивается между записями.
Владение Command WAL для финансовых команд остаётся отдельным открытым
решением, поскольку они не принадлежат инструменту. Решение обязано задать
детерминированный порядок между выводом денег из портфеля и одновременным
созданием резерва или исполнением сделки; локальных sequence независимых WAL
для этого недостаточно.

Все записи одного Command WAL имеют одинаковый канонический `payload_size`,
достаточный для самой большой команды текущей версии схемы. Короткая команда
обнуляет неиспользованный хвост payload. Переменной длины в `RecordHeader` нет;
канонический размер не выводится из native `sizeof(CommandWalPayload)`.

Каждый `CommandWalPayload` содержит `ClientId`, зафиксированный Ingress вместе
с командой. `ClientSequence` в payload отсутствует: его инвариант, проверка,
поведение при reconnect и роль в recovery пока не определены.

Ingress — единственный producer блоков команд. Persistence, PreRisk,
ReserveManager и Matcher читают одну и ту же неизменяемую команду. В отличие от
широковещательной SPMC-очереди, consumers упорядочены: каждая стадия может
обрабатывать только диапазон, опубликованный предыдущей стадией, и публикует
собственную границу для следующей.

```text
Ingress -> Persistence -> PreRisk -> ReserveManager -> Matcher
```

## Границы

Все границы — абсолютные монотонно возрастающие позиции. Каждая позиция задаёт
исключительную правую границу диапазона:

```text
tail <= reserve_checked <= risk_checked <= durable <= head
head - tail <= capacity
```

| Граница | Единственный writer | Значение |
|---|---|---|
| `head` | Ingress | Позиция после последней команды, опубликованной в ринг |
| `durable` | Persistence | Позиция после последней физически сохранённой команды |
| `risk_checked` | PreRisk | Позиция после последней команды с опубликованным риск-решением |
| `reserve_checked` | ReserveManager | Позиция после последней команды с опубликованным решением по резерву |
| `tail` | Поток Matcher | Позиция после последней окончательно обработанной команды; предыдущие слоты можно использовать повторно |

Каждая стадия обрабатывает собственный диапазон:

```text
Persistence:    [durable,         head)
PreRisk:        [risk_checked,    durable)
ReserveManager: [reserve_checked, risk_checked)
Matcher:        [tail,            reserve_checked)
```

Плоскость прогресса представляет собой цепочку SPSC-публикаций поверх общей
SPMC-плоскости данных:

```text
Ingress        -- head -----------> Persistence
Persistence    -- durable --------> PreRisk
PreRisk        -- risk_checked ---> ReserveManager
ReserveManager -- reserve_checked -> Matcher
Matcher        -- tail -----------> Ingress
```

## Блок команды

Ingress записывает команду до публикации `head`. Команда остаётся неизменяемой,
пока Matcher не продвинет `tail` и слот не станет доступен для повторного
использования.

У каждого проверочного модуля есть собственная область решения внутри блока.
Модуль может записывать только собственный результат.

```cpp
struct CommandRingSlot {
    CommandEnvelope command;  // Ingress; sequence + immutable WAL payload
    RiskResult risk;          // PreRisk; runtime-only sidecar
    ReserveResult reserve;    // ReserveManager; runtime-only sidecar
};

enum class Decision : std::uint8_t {
    Pending,
    Accepted,
    Rejected,
    Skipped
};
```

Persistence записывает `CommandEnvelope::command_sequence` только в
`RecordHeader::sequence`, а `CommandEnvelope::payload` сериализует как
`CommandWalPayload`. Sequence не дублируется в payload.

`RiskResult` и `ReserveResult` — оперативные sidecar-метаданные. Они не являются
частью неизменяемого `CommandWalPayload`, не сериализуются в Command WAL и не
входят в CRC физической записи команды. Уже durable-запись Command WAL никогда
не изменяется проверочными модулями.

Разметка sidecar фиксируется версией сборки/эпохи. Динамический registry, map,
TLV и аллокации на команду не используются.

## Контракт стадии

Для каждой позиции ниже входящей границы проверочная стадия:

1. читает неизменяемую команду и решения предыдущих стадий;
2. ровно один раз записывает собственное решение;
3. публикует продвижение своей границы с release-семантикой.

Следующая стадия выполняет acquire-load этой границы до чтения решения.

```cpp
while (my_frontier < upstream_frontier) {
    auto& block = ring[my_frontier % capacity];
    block.my_result = check(block);
    publish(++my_frontier);
}
```

Если предыдущая стадия отклонила команду, каждая следующая проверочная стадия
всё равно проходит эту позицию и записывает `Skipped`. Отклонённая команда не
должна останавливать продвижение границ.

## Отказы и Matcher

Поток Matcher последовательно обрабатывает каждую полностью проверенную
позицию.

- Если хотя бы одно решение равно `Rejected`, поток публикует соответствующий
  отказ в Event tract и не передаёт команду в matching core. В этом документе
  публикация в Event WAL означает, что событие принято Event tract; физическая
  durability Event WAL относится к контракту Event tract.
- Если все обязательные решения равны `Accepted`, команда передаётся в matching
  core.
- Matcher не создаёт новые terminal rejections команды. Если команда
  отклонена, источником события отказа является проверочный модуль, принявший
  это решение.
- После того как outcome команды принят Event tract, Matcher продвигает `tail`.

Событие отказа содержит как минимум:

- sequence исходной команды;
- модуль, принявший решение об отказе;
- идентификатор причины/правила;
- эпоху;
- данные о версии модуля и ruleset, необходимые для аудита.

## Владение и освобождение

Ранние consumers не выполняют pop и не освобождают слот. Они только читают
команду, записывают собственный sidecar-результат и продвигают свою границу.

Matcher — последний consumer и единственный writer `tail`. Поэтому он же
является логическим владельцем освобождения. Общий поиск
`min(all_consumer_progress)` не нужен: инвариант упорядоченных границ
гарантирует, что `tail` всегда является минимальной позицией прогресса.

Ingress может повторно использовать слот только после acquire-load
продвинутого `tail`.

## Memory ordering и расположение в кеше

Цепочка happens-before:

```text
command
  -> head
  -> durable
  -> risk decision
  -> risk_checked
  -> reserve decision
  -> reserve_checked
  -> matcher consumption
  -> tail
  -> slot reuse
```

У каждой границы ровно один writer. Границы, которые изменяются разными
потоками, должны находиться в разных cache lines. Стадия публикует данные до
release-store своей границы; следующая стадия выполняет acquire-load границы до
чтения этих данных.

Результаты последовательных проверок могут находиться рядом: их writers
упорядочены границами и не пишут одновременно. Если в будущем появятся
параллельные проверки, независимо записываемые области результатов не должны
разделять одну cache line.

## Ёмкость и распространение отказов

Ринг заполнен, когда:

```text
head - tail == capacity
```

Центральный оркестратор ресурсов не требуется. Остановившаяся стадия естественно
останавливает все нижележащие границы; вышележащие стадии постепенно заполняют
ринг, после чего Ingress получает `Full` и применяет собственную политику
деградации/back-pressure.

Ошибка Persistence не продвигает `durable`. PreRisk, ReserveManager и Matcher
могут завершить уже опубликованную работу в пределах своих границ, но ни одна
команда после последней durable-позиции не может попасть в Matcher.

## Эпохи и replay

Код, правила, конфигурация, схемы и начальное состояние, влияющие на
детерминированное преобразование Command WAL в Event WAL, неизменяемы внутри
эпохи. Manifest эпохи идентифицирует точную сборку движка, версии модулей,
rulesets, версии схем, хеши конфигурации и начальный snapshot.

Команды и события содержат `epoch_id`, но не повторяют полный manifest. События
отказа дополнительно содержат непосредственно относящиеся к решению сведения о
модуле и правиле.

- Event replay применяет уже записанные события и не запускает повторно
  PreRisk, ReserveManager или Matcher.
- Command replay требует точную сборку, rulesets, конфигурацию и начальное
  состояние исходной эпохи. Базовое предположение: при Command replay
  ReserveManager запускается заново из snapshot исходной эпохи.
- Изменение любого детерминированного модуля или ruleset начинает новую эпоху.

Базовая процедура обновления дренирует старый конвейер и надёжно закрывает его
Event WAL до открытия новой эпохи. Одновременная обработка команд нескольких
эпох явно находится вне текущего решения.

## Следствия

- Все стадии используют один неизменяемый блок команды.
- Нет per-slot refcount и поиска прогресса независимых readers.
- Порядок и back-pressure явно выражены инвариантом границ.
- Добавление последовательного проверочного модуля требует одной фиксированной
  области результата и одной принадлежащей модулю границы.
- ReserveManager хранит состояние: создание резерва относится к конвейеру до
  Matcher, а расходование или освобождение резервов по сделкам, отменам и
  отказам требует отдельного контракта обратной связи через Event WAL.

## За границами решения

- NUMA-размещение и агрегация границ между NUMA-узлами;
- параллельные независимые validators;
- динамическая композиция конвейера;
- несколько producers;
- одновременная обработка нескольких эпох;
- подробный дизайн обратной связи и reconciliation ReserveManager;
- клиентские ответы и выходной тракт Event WAL.
