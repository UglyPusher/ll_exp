# Архитектура Event WAL

**Статус:** базовое решение принято; открытые вопросы перечислены явно  
**Дата:** 2026-08-16

## Назначение

Event WAL — авторитетная упорядоченная история результатов, произведённых
потоком Matcher. Он отделяет детерминированное исполнение команд от последующей
доставки и построения проекций.

Базовый тракт:

```text
Matcher -> Event Ring -> Persistence -> durable consumers
```

Matcher не отправляет окончательный ответ клиенту и не обновляет внешнюю
проекцию напрямую. Он публикует события. Последующее состояние и ответы
выводятся из durable-событий.

## Решение

Транспорт событий — ограниченный ринг с одним producer, одной стадией
Persistence и несколькими нижележащими consumers.

Один Event Ring и его файл Event WAL обслуживают ровно один инструмент внутри
ровно одной эпохи. `(InstrumentId, EpochId)` фиксируется конфигурацией тракта и
manifest и не повторяется в каждом `EventWalPayload`. Новая эпоха создаёт новый
файл Event WAL.

В ринге есть две разные части:

1. От Matcher до Persistence работает последовательная стадия публикации.
2. После границы `durable` обязательные consumers образуют широковещательный
   SPMC-тракт.

```text
                         +-> MarketDataProjection
Matcher -> Persistence -+-> Reserve reconciliation
                         +-> Client Egress
                         +-> другие обязательные проекции
```

Все consumers наблюдают одну и ту же неизменяемую последовательность событий.
Они продвигаются независимо и никогда не изменяют payload события.

## Роли

### Поток Matcher

Matcher — единственный producer событий. Он:

- преобразует одну упорядоченную команду в одно или несколько упорядоченных
  событий;
- назначает детерминированные event sequences;
- записывает причинную связь с исходной командой;
- удерживает не более одного последнего события текущей команды и публикует
  события в ринг с явной границей результата команды;
- после успешной публикации забывает опубликованные данные.

Поток Matcher также публикует отказы, сформированные предыдущими стадиями
командного конвейера. Сам matching core получает только принятые команды.

### Persistence

Persistence — единственный writer границы `durable`. Он:

- последовательно читает опубликованные события;
- сериализует физические записи Event WAL;
- дописывает выбранный batch;
- выполняет одну операцию физической durability для batch;
- продвигает `durable` только после полного успеха операции.

Persistence не назначает бизнес-смысл, не переинтерпретирует события и не
обновляет проекции.

### Durable consumers

Каждый обязательный consumer:

- читает только события ниже `durable`;
- обрабатывает события строго в порядке event sequence;
- применяет и подтверждает progress только для полного результата команды,
  завершённого `is_last_for_command`;
- владеет собственным progress cursor и публикует его;
- может быть независимо восстановлен из Event WAL;
- никогда не изменяет общий блок события.

Известные durable consumers:

- `MarketDataProjection`;
- reconciliation расходования и освобождения резервов;
- формирование ответов `ClientEgress`;
- будущие accounting- и client-проекции.

Метрики, tracing и другие lossy observers не являются обязательными consumers
и не должны удерживать слоты Event Ring.

## Позиции и инварианты

Все позиции абсолютны, монотонно возрастают и задают исключительную правую
границу.

```text
consumer_progress[i] <= durable <= head
head - reclaim <= capacity
```

| Позиция | Единственный writer | Значение |
|---|---|---|
| `head` | Поток Matcher | Позиция после последнего события, опубликованного в ринг |
| `durable` | Persistence | Позиция после последнего события с подтверждённой физической durability |
| `consumer_progress[i]` | Consumer `i` | Позиция после последнего события, полностью применённого этим consumer |
| `reclaim` | Вычисляемая позиция | Минимальный прогресс всех обязательных consumers |

```text
reclaim = min(consumer_progress[required consumers])
```

Если при инициализации не зарегистрировано ни одного нижележащего consumer,
границей освобождения служит `durable`. В обычном режиме присутствует как
минимум один обязательный consumer.

Matcher может использовать слот повторно только после того, как `reclaim`
прошёл его предыдущую абсолютную позицию.

## Идентичность события и причинная связь

In-memory envelope и логический payload Event WAL имеют вид:

```cpp
struct EventEnvelope {
    EventSequence event_sequence;
    EventWalPayload payload;
};

struct EventWalPayload {
    ClientId client_id;
    CommandSequence caused_by_command_sequence;
    EventIndex index_in_command;
    bool is_last_for_command;
    Event message;
};
```

- `event_sequence` равен `RecordHeader::sequence` физической записи Event WAL,
  начинается с `1`, локален этому инструменту и эпохе и не повторяется в
  `EventWalPayload`.
- `client_id` сохраняет клиента принятой команды для downstream consumers.
- `caused_by_command_sequence` идентифицирует исходную команду.
- `index_in_command` задаёт детерминированный порядок событий одной команды.
- индексы одной команды начинаются с `0`, идут без разрывов, а ровно последнее
  событие имеет `is_last_for_command == true`.
- Event sequence назначается Matcher, а не Persistence.
- Instrument, Epoch и версия схемы событий принадлежат файлу Event WAL и
  manifest и не повторяются в каждом payload.

Persistence сохраняет порядок, уже установленный Matcher.

## Payload события

Payload события неизменяем после публикации `head` потоком Matcher. Он остаётся
действительным, пока все обязательные consumers не пройдут событие и слот не
будет освобождён.

Представительные классы событий:

- `RiskRejected`;
- `ReserveRejected`;
- `OrderRested`;
- `OrderPartiallyFilled`;
- `OrderFullyFilled`;
- `TradeExecuted`;
- `OrderCancelled`;
- session- и incident-события.

Событие отказа содержит достаточно информации для аудита:

```text
sequence исходной команды
модуль, принявший решение об отказе
идентификатор причины и правила
эпоха
версия модуля
идентификатор ruleset
```

Manifest эпохи остаётся авторитетным источником полных сведений о сборке и
конфигурации. Событие отказа намеренно повторяет непосредственно относящиеся к
решению сведения о risk- или reserve-модуле.

## Публикация и memory ordering

Цепочка публикации:

```text
event payload
  -> head
  -> physical append and sync
  -> durable
  -> consumer processing
  -> consumer_progress[i]
  -> reclaim
  -> slot reuse
```

- Matcher завершает запись события до release-публикации `head`.
- Persistence выполняет acquire-load `head` до чтения события.
- Persistence завершает физическую durability до release-публикации
  `durable`.
- Consumers выполняют acquire-load `durable` до чтения событий.
- Consumer завершает свою работу до release-публикации собственного прогресса.
- Matcher получает границу освобождения с acquire-семантикой до повторного
  использования слотов.

`head`, `durable` и независимо записываемые consumer cursors не должны
разделять cache line. Позиция прогресса каждого consumer находится в отдельной
padded-области.

## Освобождение и классы consumers

Обязательные consumers участвуют в освобождении слотов и, следовательно, в
back-pressure. Потеря или остановка обязательного consumer в итоге останавливает
Matcher заполнением ринга.

Необязательные consumers не участвуют в вычислении `reclaim`. Они должны
допускать потерю данных, использовать отдельный копируемый транспорт или уметь
ресинхронизироваться из Event WAL/snapshot.

Consumer не может незаметно перейти из обязательных в необязательные или
обратно внутри одной эпохи. Набор обязательных consumers фиксируется при
инициализации и записывается в конфигурации эпохи/runtime.

Динамическая регистрация и удаление consumers не входят в базовое решение.

## Back-pressure и отказы

Event Ring заполнен, когда:

```text
head - reclaim == capacity
```

Отказы распространяются локально и механически:

- Если Persistence остановился, `durable` не движется. Consumers дочитывают
  только уже durable-диапазон. Matcher в итоге получает `Full`.
- Если остановился обязательный consumer, его progress становится `reclaim`.
  Matcher в итоге получает `Full`, даже если все остальные consumers успевают.
- Остановившийся необязательный observer не влияет на освобождение.
- При ошибке physical append или sync `durable` остаётся неизменным. Ни один
  consumer не может увидеть ошибочный диапазон как durable.

Центральный оркестратор ресурсов не требуется. Состояние здоровья
распространяется вверх по тракту через ограниченную ёмкость. Принятые состояния
yellow/red/purple могут вычисляться из заполнения ринга и состояния нижележащих
компонентов.

## Ответы клиенту

Получение команды Ingress и окончательный бизнес-результат — разные факты.

Окончательные ответы клиенту формируются из durable-событий Event WAL, а не из
прямого callback Matcher. Поэтому ответ не может заявить о результате, который
ещё не пересёк durable-границу.

Типичные результаты:

```text
RiskRejected
ReserveRejected
OrderAccepted / OrderRested
TradeExecuted
OrderCancelled
```

Сетевые повторы, подтверждение доставки, порядок ответов отдельному клиенту и
дедупликация принадлежат Client Egress и его проекции, а не Matcher или
Persistence Event WAL.

## Обратная связь резервов

ReserveManager создаёт резерв или отказывает до Matcher в командном SPMC-
конвейерном ринге. Затем события Matcher описывают использование или
освобождение резерва:

- исполнение расходует соответствующую часть резерва;
- отмена освобождает оставшийся резерв;
- терминальный отказ освобождает уже созданный резерв;
- частичное исполнение расходует часть и сохраняет необходимый остаток.

Reconciliation резервов читает durable-события. Точный порядок между этой
обратной связью и новыми решениями о резервах на командной стороне является
отдельным архитектурным решением: здесь возникает обратная связь из Event WAL в
состояние ReserveManager.

## Replay и восстановление

Event WAL — основной источник восстановления нижележащего состояния:

```text
snapshot + durable suffix Event WAL -> восстановленная проекция
```

Event replay:

- применяет записанные события в порядке event sequence;
- применяет результат команды только после проверки непрерывных индексов и
  `is_last_for_command == true`;
- отбрасывает незавершённый результат команды в конце WAL;
- не запускает повторно решения PreRisk, ReserveManager или Matcher;
- проверяет целостность физических записей и непрерывность sequence;
- останавливается при несовпадении схемы, повреждении или необъяснимом разрыве
  sequence.

Command replay — другая операция. Она повторно запускает детерминированный тракт
команд с исходной сборкой, правилами, конфигурацией и начальным состоянием эпохи,
а затем сравнивает полученный Event WAL с записанным.

## Эпохи и версии

Один Event WAL принадлежит одному инструменту и одной эпохе; `InstrumentId` и
`EpochId` не повторяются в каждом `EventWalPayload`. Manifest эпохи фиксирует
все входы, которые могут изменить детерминированное преобразование Command WAL
в Event WAL:

- сборку движка;
- версию Matcher;
- версии PreRisk и ReserveManager;
- rulesets и лимиты;
- схемы команд и событий;
- конфигурацию инструмента;
- начальный snapshot и другие reference data.

Изменение модуля, правила, схемы или детерминированной конфигурации начинает
новую эпоху. Базовая процедура дренирует и надёжно закрывает старые командный и
событийный тракты до запуска новой эпохи.

## Event batches

Одна команда может породить несколько упорядоченных событий. Вместе они
образуют один логический результат команды:

```text
Command N -> Event N.0, Event N.1, ... Event N.k
```

Matcher удерживает одно последнее событие текущей команды. При появлении
следующего события предыдущее публикуется с `is_last_for_command == false`; при
завершении команды последнее публикуется с `is_last_for_command == true`.
Отдельного `CommandCompleted` event нет.

Consumers могут прочитать или сделать durable префикс multi-event результата,
но не должны применять его как завершённый бизнес-результат до последнего
события. После аварии recovery проверяет одинаковые `ClientId` и
`caused_by_command_sequence`, непрерывные индексы от `0` и конечный флаг. Хвост
после последнего полностью проверенного результата команды обрезается.

Каждая принятая команда обязана породить хотя бы одно событие. Поэтому
`ShutdownCommand` публикует `ShutdownEvent`. `CommandReaderFatal` не имеет
принятой команды и сообщается out-of-band, а не записывается с искусственными
нулевыми идентификаторами.

## Открытые решения

1. **Обязательные consumers.** Окончательно определить, какие проекции участвуют
   в освобождении. В частности, решить, является ли Client Egress обязательным
   или может независимо восстановиться и продолжить чтение Event WAL.
2. **Порядок обратной связи ReserveManager.** Определить единый
   детерминированный порядок между новыми резервами на командной стороне и
   durable-feedback сделок, отмен и отказов.
3. **Snapshot consumer.** Решить, является ли создание snapshot обязательным
   consumer ринга или работает с независимо поддерживаемой проекцией.
4. **Consumer checkpoints.** Определить, какие progress-позиции должны быть
   durable и как они восстанавливаются без пропуска событий.

## Следствия

- Matcher остаётся детерминированным single writer.
- Ни одна нижележащая проекция не может увидеть недюрабельный результат.
- Обязательные проекции получают каждое событие в одном и том же полном порядке.
- Медленный обязательный consumer создаёт ограниченный back-pressure вместо
  потери данных.
- Необязательная телеметрия не может остановить движок.
- Event replay восстанавливает проекции без старых проверочных модулей.
- Освобождение сложнее, чем в командном SPMC-конвейерном ринге: Event WAL
  использует минимум прогресса независимых обязательных consumers.

## За границами решения

- подробный физический формат записей Event WAL;
- транспортный протокол Client Egress;
- формат snapshot;
- реализация accounting;
- агрегация consumers между NUMA-узлами;
- динамические consumers;
- репликация и удалённые followers Event WAL;
- точный алгоритм reconciliation ReserveManager.
